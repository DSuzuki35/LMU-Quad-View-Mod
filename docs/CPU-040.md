# CPU work and frametime spikes in 0.4.0

The two additional focus views still require LMU scene traversal and drawing. Existing captures measured about 2.05 ms elapsed wall time for both focus hooks, of which 1.99 ms was inside native scene rendering. These nested scopes include driver/runtime waits and do not establish a matched mod-on/off CPU cost.

Implemented reductions:

- Cached outer-bank validation no longer probes COM interfaces that the bank already retains with AddRef, when all native wrapper/container/vector/interface identities still match. New interfaces are validated before any COM call. The WARP regression drops from 31 memory probes to 20, including zero redundant retained-interface probes. Interleaved optimized synthetic tests measured around 3–4 microseconds saved per cached prepare; this is not a measured game frametime improvement.
- Hiding the benchmark overlay now stops GDI bitmap rendering and pixel publication. Measurement, recording and configuration continue. Showing it publishes fresh pixels on the next tick. The launcher also stops refreshing its preview when that page is hidden or the window is minimized.
- Explicit profiling adds `outer_lock0/1` and separate menu buckets to distinguish time waiting for the global XR state lock from the existing runtime-image `outer_wait0/1` measurement. These are inclusive wall times, not exclusive CPU utilization. Profiling off retains zero clock/GPU-query behavior.

Other candidates need evidence and lifecycle work: synchronous diagnostic bursts, the runtime outer-image wait under the state mutex, capture-end sorting/flushing, descriptor caching, and native duplicate traversal/draw submission. Removing image waits, restoration or validation would risk invalid images and is not an optimization.

For a useful A/B, keep the replay, graphics, runtime, provider, focus/crop dimensions and overlay visibility identical. Compare diagnostics off first with external timing, then perform a separate diagnostic capture to identify the costly stage. Include median, p95/p99, spike frequency and whether the spike appears in native scene work, lock wait, image wait or provider submission.

## SPS and NVIDIA Multi-View Rendering

Single-pass instancing can reduce duplicate CPU draw submission; NVIDIA MVR can project a geometry stream into up to four views. Hardware capability alone does not eliminate LMU's native per-eye traversals. The portable offscreen two-eye proof and guarded shader conversion already work, but replacing native draws still needs a paired scheduler, compatible shaders, union visibility, eye-specific state and correctly owned render targets. The current converter targets two-eye routing; it is not a four-view MVR implementation.

The local RTX 5090 passes the existing portable hardware proof and reports NVAPI SPS/MVR support. This is not a live LMU speedup. The optional capability command in PortableStereoCheck queries support without enabling modes or changing the game.

References: [NVIDIA Single Pass Stereo](https://developer.nvidia.com/vrworks/graphics/singlepassstereo), [NVIDIA Multi-View Rendering](https://developer.nvidia.com/vrworks/graphics/multiview), [renderer implementation handoff](../INSTANCED-STEREO-HANDOFF.md).
